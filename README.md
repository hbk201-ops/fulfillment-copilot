# 服务履约质量智能运营助手 · fulfillment-copilot

> 把一站式到家服务「**下单 → 预约 → 约定上门时段 → 派单 → 上门 → 完工 → 评价**」全链路的
> **履约质量监控、异常归因、站点运营分析与 AI 报告生成**，做成一条可复现、可审计、零依赖的分析流水线。

## 30 秒看懂

```bash
git clone <你的仓库地址> && cd fulfillment-copilot
python run.py demo          # 一条命令跑通全流程（零依赖、零配置，不需要 API Key）
```

2 万单合成数据、5 大服务品类、6 个服务站点，**约 7 秒**产出：

- **HTML 看板**（单文件，双击即开）：`output/dashboard.html`
- **运营报告**（Markdown）：周报 / 异常专报 / 用户声音洞察 / 智能派单建议 / 3 份 BRD 需求文档草稿
- **Excel 工作簿**（10 个 Sheet，带条件格式）：`output/kpi_workbook.xlsx`

样例产物已直接提交在 [`examples/`](examples/)，**不跑代码也能评估**。

> `run.py` 只是把 `src/` 加进模块搜索路径，因此**无需安装任何东西**即可运行；
> 若你更习惯标准方式：`pip install -e .` 之后可以用等价的 `fulfillment-copilot demo`。

## 为什么做这个项目

一站式服务（家电家居安装、充电桩、家庭维修、3C 服务、搬家）的履约质量，难点从来不是"没有数据"，而是：

1. **口径不统一**：同一个"准时率"在周报、日报、站点考核里算法不同，会上先吵口径再谈问题；
2. **异常发现靠人**：等客诉集中爆发才知道某个站点出问题，发现时延以周计；
3. **定位不到原因**：知道"准时率跌了"，但不知道是哪个站点、哪个品类、哪批工程师；
4. **只报不闭环**：周报每周提同一个问题，没人负责、没有时限、没有验证；
5. **AI 用得很虚**：让 AI 直接写周报，数字靠编，出了错还查不出来。

这个项目把这五件事各解一遍：**统一口径的指标注册表 + 双层异常检测 + 贡献度归因下钻 + 动作到责任方与时限 + "程序算事实、AI 写叙述"的报告链路。**

## 快速开始

**环境要求：Python 3.10+。核心分析链路零第三方依赖。**

```bash
# 1) 一键跑通：生成数据 → 算指标 → 检测异常 → 归因 → 全部报告
python run.py demo --orders 20000

# 2) 打开看板（Windows 直接双击；其它系统用浏览器打开）
start output/dashboard.html

# 3) 自检：验证异常检测是否抓到内置的异常剧本（CI 同款）
python run.py verify
```

常用子命令（`python run.py <命令>`，安装后等价于 `fulfillment-copilot <命令>`）：

| 命令 | 作用 |
|---|---|
| `demo` | 一键产出全部交付物（推荐） |
| `kpi` | 只打印核心指标与站点/品类/城市分层对比 |
| `anomaly` | 只输出异常清单、归因下钻与需跟进工单 |
| `verify` | 对照注入的异常剧本，自检检测效果（3/3 命中） |
| `report --type weekly\|anomaly\|feedback\|dispatch` | 生成指定报告 |
| `brd --topic dispatch\|alert\|appointment` | 生成 BRD 需求文档草稿 |
| `dashboard` / `excel` | 单独导出看板 / Excel |
| `gen-data` | 只生成工单明细 CSV 与注入异常说明 |

**Excel 导出（可选）**：`pip install openpyxl`。不装也能跑通全流程，只是跳过 `.xlsx`（会明确提示，不会静默失败）。

**用你自己的数据**：`python run.py kpi --data your_orders.csv`（列名见 `examples/data/orders_sample.csv`）。

**接入真实大模型**（可选，不配也能跑，报告由确定性模板生成）：

```bash
export FQC_LLM_BASE_URL=https://api.deepseek.com/v1
export FQC_LLM_API_KEY=sk-xxxx
export FQC_LLM_MODEL=deepseek-chat
python run.py report --type weekly --provider openai
```

## 本项目样例数据的关键结论（2 万单 / 84 天 / 6 站点）

| 指标 | 值 | 指标 | 值 |
|---|---|---|---|
| 履约质量综合得分 | **92.9（A 级）** | 全链路 SLA 达成率 | 95.1% |
| 上门准时率 | 91.2% | 一次完工率 | 95.9% |
| 客诉率 | 2.1% | 差评率 | 4.9% |
| 服务 NPS | 84.6 | 毛利率 / 单均成本 | 31.9% / 280.9 元 |
| 统计预警命中 | 20 项（高/中/低分级） | 需跟进异常工单 | 3970 单（19.9%） |

**内置的三个异常剧本全部被自动识别**（`python -m fulfillment_copilot verify` 可复现）：

| 严重度 | 异常 | 基线 → 当前 | 偏离 | 归因结论 |
|---|---|---|---|---|
| 高 | 品类「充电桩服务」返工率 | 5.1% → 20.2% | +300.6% | 一次完工率下降，归因指向工程师技能与新品类培训不足 |
| 高 | 站点「广州粤通服务商」派单时长 P90 | 5.3h → 9.9h | +85.3% | 下钻到站内 **个别工程师**（E01/E02/E03），而非"整个站点都不行" |
| 高 | 品类「搬家」毛利率 | 32.0% → 7.2% | −77.6% | 单均成本上涨 35.9%（533.9 → 725.7 元），需复核结算规则与运力采购价 |

**另一个值得注意的交叉验证**：广州粤通"单/人/天"最高（4.5 单），但综合得分最低（89.3）——
只看人效会误判为标兵，结合质量指标才发现是**超负荷运转导致质量下滑**。多维交叉验证是避免误判的关键，
详见 [`docs/04_直营站点运营指标.md`](docs/04_直营站点运营指标.md)。

## 技术设计要点

### 1. 数据模型：把业务事件拆对

`下单 → 预约受理 → **约定上门时段** → 派单 → 上门 → 完工 → 评价`。

把"预约受理"与"约定上门时段"拆成两个字段，是因为**准时率必须以承诺的上门时段为基准**。
开发初期两者合并，导致准时率被算成 0.4%——这个坑记录在 [`docs/01`](docs/01_指标体系与口径.md) 第六节。

### 2. 指标体系：口径单一来源

23 个指标的名称/单位/方向/目标值集中在 `METRICS` 注册表，报告、异常检测、归因、Excel **共用同一实现**；
分母为 0 时返回 `None` 而不是 `0`（不把"没有样本"当成"表现差"）。

### 3. 异常检测：规则 + 统计，且防误报

- 规则引擎负责"不漏"（11 类工单级异常，超时倍数分级）；
- 统计预警负责"发现慢慢变坏"（近 14 天 vs 前 56 天基线，稳健 z-score 用**中位数/MAD** 抗离群）；
- **双门槛**：偏离 ≥ 30% 且（z ≥ 2.5 或偏离 ≥ 60%），并要求样本量 ≥ 50；
  在小样本上实测过——不加门槛时随机波动能把客诉率放大到 +295%，真异常被噪声淹没。

### 4. 归因下钻：贡献度排序 + 自动跳过无区分度维度

`贡献度 = 组内单量占比 × max(0, 与同行的差距) / |同行值|`；
与异常维度 1:1 的维度（如站点异常再按城市拆）自动跳过，避免"贡献 100%"这类废话归因。

### 5. AI 层：程序算事实，AI 写叙述

```
程序：指标/异常/归因（可复现、可审计）
        ↓  结构化「证据包」
AI  ：提示词（五段式 + 硬约束 + 版本化）→ 报告
        ↓  模型不可用时
回退：确定性模板（报告永不开天窗）
```

**为什么不直接让 AI 写周报**：数字会编、结果不可复现、出错查不出来。
本项目里指标值与表格由程序渲染，模型只负责解释、建议与叙述；`--no-ai` 可一键对比"AI 到底带来了什么增量"。

## 测试与 CI

```bash
python -m pytest tests        # 102 个测试，约 8 秒
python -m unittest discover -s tests   # 不装 pytest 也能跑
```

测试不是"跑一遍不报错"，而是**断言业务语义**：

- 手工构造 4 笔已知工单，逐项精确断言指标口径（准时率 2/3、返工率 1/3、P90 = 28.4h…）；
- 对照注入的异常剧本，断言**三个剧本全部被识别**（漏检即 CI 失败）；
- 断言负面反馈文本的主题识别率（回归测试：防止"没有信息量的差评"污染主题分布）；
- 断言模型失败时**自动回退**且报告小节完整；
- CLI 端到端跑通并检查产物文件。

CI 分两个任务：**零依赖任务**（不装任何第三方包，跑 unittest + 全流程 + 自检）与**完整任务**（装 openpyxl + pytest，跑测试并归档看板/报告/Excel）。

## 局限与诚实说明

1. **全部使用合成数据**。真实履约明细涉及用户隐私与商业机密，不可能放进公开仓库。
   为此我把"注入的异常剧本"随数据一起输出（`examples/data/ground_truth.json`），
   让检测效果**可验证**而不是自说自话；
2. **指标阈值基于合成数据设定**，不代表真实业务结论，需要在你自己的数据上重新校准；
3. **反馈主题分类基于关键词词典**，对反讽、方言、超长文本鲁棒性有限。
   合成数据里"其他"类只占 1.1%，但真实场景通常会到 10~20% —— 那正是该上模型的场景；
4. **派单建议是可解释评分卡，不是模型排序**。在没有足够"正确派单"标注数据前，坚持可解释优先；
5. 报告的动作与责任方是**建议**，最终排期与资源投入仍需业务判断——AI 不该替人做决策。

## 5 分钟面试讲解脚本

> "这个项目解决的是服务履约里最常见的五个问题：口径不统一、异常靠人发现、定位不到原因、只报不闭环、AI 用得虚。"

1. **先讲痛点与结论**（40 秒）：打开 `examples/dashboard.html`，指着综合得分 92.9 和 20 项异常说结果；
2. **讲口径**（60 秒）：翻到 `docs/01`，说明 23 个指标集中在注册表里、分母为 0 返回空值，
   再讲"预约受理 vs 约定上门时段"这个真实踩坑（准时率从 0.4% 修到 91%+）；
3. **讲异常闭环**（60 秒）：`docs/02` 的六步闭环，重点讲**统计预警的双门槛**——
   为什么加样本量与显著性门槛（小样本噪声会把客诉率放大 295%）；
4. **讲归因**（60 秒）：打开周报里的归因表，说明 S03 派单恶化的贡献度排序如何指认到具体工程师，
   以及"无区分度维度自动跳过"的工程细节；
5. **讲 AI 的分工**（60 秒）：打开 `docs/03`，说明"程序算事实、AI 写叙述"、提示词五段式与硬约束、
   模型失败自动回退——**不吹 AI，而是讲怎么让 AI 可控**；
6. **讲站点运营**（40 秒）：`docs/04` 里直营质量好但毛利低 10.6pp 的取舍，
   以及"人效最高 ≠ 最优"的交叉验证案例。
