# 01 · 指标体系与口径

> 这份文档回答三个问题：**监控什么、怎么算、口径怎么不跑偏。**
> 所有指标在代码里由 `src/fulfillment_copilot/metrics.py` 的 `METRICS` 注册表统一定义，
> 报告、异常检测、归因、Excel 导出**共用同一套实现**——这是避免"同一个指标在不同报表里算法不一致"的根本手段。

---

## 一、设计原则

| 原则 | 具体做法 | 反面案例 |
|---|---|---|
| **口径单一来源** | 指标的名称/单位/方向/目标值集中在 `METRICS` 注册表 | 周报按"下单到完工"，日报按"派单到完工"，数字永远对不上 |
| **缺失值安全** | 分母为 0 时返回 `None`（样本不足），不返回 0 | 新站点只有 3 单、0 客诉，被算成"客诉率 0% 表现最好" |
| **方向显式声明** | 每个指标标注 `up_better` / `down_better` | 把"返工率上升"当成改善 |
| **可行动** | 每个指标都能指向一个责任岗位与一个动作 | 监控了 50 个指标，没人知道该做什么 |
| **分层可下钻** | 全局 → 站点 → 品类 → 城市 → 工程师 | 只报大盘，问题定位不到人 |

---

## 二、全链路环节与监控指标

链路：**下单 → 预约受理 → 约定上门时段 → 派单 → 上门 → 完工 → 评价**

| 环节 | 指标 | 计算口径 | 方向 | 目标 |
|---|---|---|---|---|
| 整体 | 工单量 | 期间内下单工单数 | — | — |
| 预约 | 预约时长 P90 | 下单 → 预约受理的小时数第 90 分位 | 越小越好 | 按品类承诺 |
| 预约 | **上门准时率** | 实际上门时间 ≤ **约定上门时段 + 品类到达窗口** 的工单占比 | 越大越好 | ≥ 95% |
| 派单 | 派单时长 P50 / P90 | 下单 → 派单的小时数分位数 | 越小越好 | 按品类承诺 |
| 派单 | 派单及时率 | 派单时长 ≤ 品类派单承诺的工单占比 | 越大越好 | ≥ 95% |
| 上门 | 上门迟到率 | 实际上门晚于约定时段 + 窗口的工单占比（= 1 − 准时率） | 越小越好 | ≤ 5% |
| 完工 | 完工时长 P90 | 上门 → 完工的作业小时数第 90 分位 | 越小越好 | 按品类承诺 |
| 完工 | 全链路时长 P50 / P90 | 下单 → 完工的小时数分位数 | 越小越好 | — |
| 完工 | 全链路 SLA 达成率 | 全链路时长 ≤ 品类时效承诺的工单占比 | 越大越好 | ≥ 95% |
| 质量 | **一次完工率** | 首次上门即解决、无返工的完工工单占已完工工单比 | 越大越好 | ≥ 92% |
| 质量 | 返工率 | 产生二次作业的完工工单占比 | 越小越好 | ≤ 5% |
| 质量 | 改约率 | 改约次数 ≥ 1 的工单占比 | 越小越好 | ≤ 8% |
| 质量 | 取消率 | 履约过程中取消的工单占比 | 越小越好 | ≤ 3% |
| 体验 | **客诉率** | 产生客诉的工单占比 | 越小越好 | ≤ 2% |
| 体验 | 差评率 | 评分 ≤ 2 的工单占**已评价**工单比 | 越小越好 | ≤ 2% |
| 体验 | 好评率 | 评分 ≥ 4 的工单占已评价工单比 | 越大越好 | ≥ 90% |
| 体验 | 平均评分 | 已评价工单的算术平均 | 越大越好 | ≥ 4.6 |
| 体验 | 服务 NPS | (好评数 − 差评数) / 已评价数 × 100 | 越大越好 | — |
| 成本 | 单均收入 / 单均成本 | 工单收入（成本）的算术平均 | 收入越大越好、成本越小越好 | — |
| 成本 | 毛利率 | (总收入 − 总成本) / 总收入 | 越大越好 | ≥ 35% |

> 口径细节：`一次完工率`/`返工率` 的分母是**已完工**工单；`差评率`/`好评率`/`NPS` 的分母是**已评价**工单
> （本项目约 86% 的完工工单会被评价）。分母不同却放在一起比大小，是最常见的分析错误。

## 三、综合得分模型（用于站点/品类横向对标）

达成率打分法：每个指标按"是否达标"折算成 0~100 分，再按分项权重加权。

| 分项 | 权重 | 构成指标 |
|---|---|---|
| 时效 | 40% | 上门准时率、全链路 SLA 达成率、派单及时率 |
| 质量 | 35% | 一次完工率、返工率 |
| 体验 | 25% | 客诉率、差评率、好评率 |

打分规则：

- 越大越好的指标：`得分 = min(1, 实际值 / 目标值) × 100`
- 越小越好的指标：`得分 = min(1, 目标值 / 实际值) × 100`（实际值为 0 记 100 分）
- 等级：A ≥ 90，B ≥ 80，C ≥ 70，其余 D

**为什么用达成率而不是 z-score？** 因为站点负责人要能一眼看懂"我差在哪"，而不是听一个统计量。
统计显著性交给异常检测（见 `02_异常管理闭环SOP.md`），考核对标用达成率——两件事分开，避免混用。

## 四、分层下钻维度

| 维度 | 用途 | 注意 |
|---|---|---|
| 站点 | 站点横向对标、直营 vs 加盟 | 站点与城市可能 1:1，下钻时会自动跳过无区分度的维度 |
| 品类 | 家电家居安装 / 充电桩 / 家庭维修 / 3C / 搬家 | 品类之间时长不可直接比，必须按各自 SLA 判定 |
| 城市 | 区域对比、区域资源投放 | 样本量小的城市不参与排名 |
| 工程师 | 派单优先级、质量帮扶 | 需设最小样本量（默认 30 单），否则"运气"会被当成"能力" |

## 五、阈值与运营规则可配置

所有阈值放在 `config/thresholds.json`，业务同学可直接改，**不需要改代码**：

```json
{
  "sla":           { "家电家居安装": { "dispatch_hours": 4, "arrive_window_hours": 1, ... } },
  "anomaly":       { "robust_zscore_threshold": 2.5, "mom_change_threshold": 0.3, "min_sample_size": 50 },
  "scorecard":     { "weights": { "timeliness": 0.4, "quality": 0.35, "experience": 0.25 } }
}
```

调整建议：

- **收紧时效承诺**（如充电桩 finish 6h → 4h）会同时抬高"完工超时"命中量与准时率压力，需评估工程师产能；
- 调高 `min_sample_size` 会减少误报、但也会漏掉小站点的问题；
- 权重调整等于改变考核导向，必须同步沟通（例如把体验权重从 25% 提到 35%，会明显影响站点排名）。

## 六、三个真实踩过的口径坑（本项目开发中实际发生并修复）

### 坑 1：把"预约受理时间"当成"约定上门时段"

最初数据模型里只有一个 `预约时间`，既当"预约成功时刻"，又当"承诺上门时间"，
结果**上门准时率被算成 0.4%**——因为几乎所有工单都被判成"迟到 17 小时"。

**修复**：拆成两个业务事件——`appoint_time`（预约受理完成）与 `promised_time`（约定上门时段），
准时判定以 `promised_time` 为基准。修复后准时率回到 90%+ 的合理区间。

**教训**：业务事件要按"用户能感知的不同时刻"拆开，不能为了省字段合并。

### 坑 2：把"没有样本"当成"表现差"

早期比率计算在分母为 0 时返回 `0`，导致新站点/新工程师的"客诉率 0%"看起来最好，
而"差评率分母为 0"又会被算成 0 分。**修复**：统一返回 `None`，并在考核中排除样本不足的单元。

### 坑 3：同一指标在两张表里算法不一致

规则引擎里"上门迟到"的延迟是用 `预约受理时间` 算的，而指标模块已经改成 `约定上门时段`——
同一个"迟到"，异常清单和监控报表给出的数值不同。
这个问题是**单元测试抓出来的**（断言迟到 2.5h 应为"中"严重度，实际算成了 19.5h）。

**修复**：规则引擎复用 `Order.arrive_delay_hours`，与指标模块同源。
**教训**：口径统一不是写在文档里就算数，要有机制保证——本项目的机制是"口径集中在 `METRICS` + 单元测试断言"。
