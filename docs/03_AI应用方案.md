# 03 · AI 应用方案

> **一句话主张：把事实交给程序，把叙述交给模型。**
> 指标口径、异常检测、归因计算全部由代码完成且可复现；AI 只负责它真正擅长的事——
> 把结构化证据组织成有观点、有动作、能给人看的文字。

这也是它和"直接用聊天工具让 AI 写周报"的本质区别：**AI 不在没有数据的地方编，而是在有数据的地方写。**

---

## 一、AI 用在哪五个场景（对应岗位职责）

| 场景 | 落地函数 | 输入 | 输出 | 对应 JD |
|---|---|---|---|---|
| 周期性数据分析 | `ai.workflows.weekly_report` | 证据包 | 周报（结论/异常/声音/动作） | AI 辅助数据分析 |
| 异常归因解释 | `anomaly_briefing` | 证据包 + 归因结果 | 异常专报（含事实与推测分离） | 异常归因、流程诊断 |
| 用户反馈归纳 | `feedback_insight` | 评价文本统计 | 主题洞察 + 典型原声 | 用户反馈分析 |
| 需求文档撰写 | `brd_draft` | 证据包 + 主题 | BRD 草稿（7 个小节 + FR 编号） | 参与业务需求文档撰写 |
| 智能调度建议 | `dispatch_advice` | 派单评分卡 + 规则 | 派单策略与风险兜底 | AI 在智能调度的应用 |

> 注意：**离线也能全部跑通**。默认的"证据包 → 确定性模板"路径不调用任何模型，
> 面试官或业务方 `python -m fulfillment_copilot demo` 一条命令就能复现全部产物。

## 二、架构：证据包是唯一的事实来源

```
   ┌──────────────────────────── 程序（可复现、可审计） ────────────────────────────┐
   │  合成/真实数据 → 指标计算(metrics) → 异常检测(anomaly) → 归因下钻 → 反馈分析    │
   │                              ↓                                                 │
   │                    build_evidence()  ← 结构化「证据包」                         │
   └──────────────────────────────┬────────────────────────────────────────────────┘
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
   ┌────────────────────┐                  ┌──────────────────────────┐
   │ 离线通道（默认）    │                  │ 模型通道（可选）          │
   │ 确定性模板渲染      │                  │ 提示词 + 证据包 + 初稿    │
   │ 零成本 / 零依赖     │                  │ 生成叙述型报告            │
   └────────────────────┘                  └────────────┬─────────────┘
              │                                        │
              └──────────────► 报告 Markdown ◄─────────┘
                                  │  失败自动回退
                                  ▼
                        HTML 看板 / Excel / BRD
```

证据包（`build_evidence`）字段：

```jsonc
{
  "meta":       { "anchor": "...", "window_days": 84, "orders": 20000, "sites": 6, "direct_sites": 2 },
  "overview":   { "arrive_ontime_rate": { "name": "上门准时率", "value": 0.913, "display": "91.3%" }, ... },
  "scorecard":  { "total": 92.8, "grade": "A", "components": { "timeliness": { "score": 95.7 } } },
  "dimensions": { "站点": [...], "品类": [...], "城市": [...], "站点类型": [...] },
  "trend":      [ { "period": "2026-W34", "arrive_ontime_rate": 0.91, ... } ],
  "anomalies":  { "rule": {...}, "dimension": [...], "attributions": [...] },
  "feedback":   { "themes": [...], "negative_rate": 0.047, "examples": {...} },
  "dispatch":   { "sites": [...], "engineers": [...], "rules": [...] }
}
```

**为什么要结构化？** 三个好处：

1. 换模型不改计算、改计算不改模板——两个方向解耦；
2. 提示词里注入的是**已算准的数字**，模型没有"自由发挥"的空间；
3. 报告里出现的每个数字都能在证据包里找到出处，可复核。

## 三、提示词工程规范（Prompt as Code）

每条提示词固定五段式，并带版本号（`prompts.PROMPT_VERSION`）：

```
角色（谁在写） → 任务（写什么） → 证据（依据什么） → 输出结构（固定小节） → 硬约束
```

本项目所有提示词共享同一段硬约束：

1. 只能使用证据包中出现的数字与名称，**不得编造**；证据不足就写"证据不足，需补充数据"；
2. 每个结论必须能被指标或异常条目支撑，并标注依据；
3. **区分事实与推断**，推断部分用「推测：」开头；
4. 动作要写到"动作 + 责任方（岗位）+ 建议完成时间"；
5. 输出 Markdown，小节标题固定，总长度 ≤ 900 字。

另外两个工程细节：

- **注入初稿**：调用模型时会把"程序生成的初稿"一起给它，要求"在此基础上改进，不增删小节"。
  这样即使模型能力一般，小节的完整性与关键数字也不会丢——这是把模型当"改写器"而不是"出题器"；
- **压缩证据包**：`evidence_digest()` 只保留报告需要的字段（异常 Top6、趋势近 8 周等），
  控制 token 成本，同时减少噪声干扰。

配套的单元测试会断言："提示词包含硬约束"、"提示词包含真实指标值"、"报告包含全部小节"——
提示词改动是可回归的。

## 四、模型接入与成本控制

```bash
# 默认：离线模板（无需任何配置）
python -m fulfillment_copilot report --type weekly

# 接入兼容 OpenAI 协议的服务（DeepSeek / OpenAI / 通义 等）
set FQC_LLM_BASE_URL=https://api.deepseek.com/v1
set FQC_LLM_API_KEY=sk-xxx
set FQC_LLM_MODEL=deepseek-chat
python -m fulfillment_copilot report --type weekly --provider openai
```

工程考虑：

- **协议统一**：只依赖 `POST {base_url}/chat/completions`，因此换供应商只改环境变量，代码零改动；
- **超时与降级**：`FQC_LLM_TIMEOUT` 默认 60s；任何异常（网络/鉴权/返回结构异常）都会被捕获，
  **自动回退到模板版本**，并在报告里注明"大模型生成失败，已回退"——报告永不开天窗；
- **成本意识**：周报只发一次请求、证据包做压缩；批量场景（如逐单归因）默认不调用模型，
  只在对 Top 异常做深度分析时才用模型，把 token 花在"值得花"的地方；
- **可关断**：`--no-ai` 强制走模板，便于对比"模型到底带来了什么增量"。

## 五、幻觉防控（四条）

| 风险 | 对策 |
|---|---|
| 编造数字 | 只用证据包数字；提示词硬约束；报告里的指标值由程序渲染，不由模型生成 |
| 编造站点/人名 | 证据包只提供真实存在的站点、工程师 ID |
| 把推测当结论 | 强制「事实 / 推测：」二分标注 |
| 模型不可用导致断流 | 全链路异常捕获 + 模板回退 + 报告内标注 |

> 一条经验：**凡是需要精确的地方，都不要让模型输出**。
> 指标值、表格、异常清单全部程序渲染；模型只写"解释、建议、动作"这类需要语言组织能力的内容。

## 六、和"直接让 AI 写周报"的对比

| 维度 | 直接让 AI 写 | 本项目做法 |
|---|---|---|
| 数据准确性 | 取决于有没有把数据贴全，易编造 | 指标由程序算，模型只引用 |
| 可复现 | 同样输入两次结果不同 | 离线通道完全确定性；模型通道可 diff |
| 可审计 | 说不清数字怎么来的 | 每个数字可回溯到证据包与计算代码 |
| 成本 | 每次都要塞全量数据 | 证据包压缩 + 只在必要时调用模型 |
| 失败影响 | 模型挂了就交不出周报 | 自动回退模板，报告照常产出 |
| 维护 | 提示词散落在聊天记录里 | 提示词版本化 + 单元测试 |

## 七、Roadmap：从"能用"到"好用"

按投入产出排序：

1. **反馈语义分类**（当前：词典 + 规则）
   真实场景中"其他"类含糊反馈会占到 10~20%，正是该上模型的场景：
   先用小样本标注 500 条，比较"词典 / 微调小模型 / 大模型 few-shot"的准确率与成本，再决定方案。
2. **派单从规则评分到模型排序**
   现状是可解释评分卡。等系统积累 3~6 个月的"派单结果 + 履约质量"数据后，
   把它变成 learning-to-rank 问题；**在此之前不做黑盒**，因为一线无法理解、无法申诉。
3. **异常归因的自动化 Agent**
   当前归因维度是预设的（品类/工程师/城市）。下一步可让模型基于"当前异常 + 可用维度"
   自主决定下钻路径，但每一步的数值仍由程序计算。
4. **建立评测集**
   为报告质量建立人工评分卡（数字准确性 / 动作可执行性 / 无幻觉），
   每次改提示词跑一遍回归——让"AI 输出质量"也变成可测量的。
5. **私有化与合规**
   用户评价原文包含个人信息，直接送公有云模型存在合规风险：
   生产环境应走**先脱敏（手机号/地址/姓名）再调用**，或使用企业内部私有化部署的模型。

## 八、诚实的局限

- 本项目的语料与数据是**合成数据**，用于演示方法链路，指标阈值不构成对真实业务的结论；
- 离线模板生成的报告"事实准确但语言平实"，模型通道的优势在于叙述与洞察的连贯性，
  具体提升幅度需要在你自己的数据上做 A/B 评测；
- 反馈主题分类基于关键词词典，对反讽、方言、超长文本的鲁棒性有限（已在 Roadmap 中规划改进）；
- AI 不能替你做决策：报告给出的动作与责任方是**建议**，最终排期与资源投入仍需业务判断。
